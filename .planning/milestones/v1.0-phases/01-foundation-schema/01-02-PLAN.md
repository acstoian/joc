<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anon role -> questions.correct_option | Guests must not learn the correct answer before the host reveals it. |
| anon role -> answers | Guests may INSERT their own answer; they must not read/modify others' answers via anon. |
| Application code -> DB constraints | Even a buggy/bypassed API must not be able to create a duplicate answer or duplicate join. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-05 | Information Disclosure | anon reading `questions.correct_option` before reveal (answer-sniffing / cheating) | mitigate | RLS: anon SELECT on base `questions` denied; anon reads only via the `questions_public` view which omits `correct_option`. Server broadcasts the correct option only at reveal time (Phase 3). Verified with the ANON key (not service role) in Plan 03. (D-12, PITFALLS #11) |
| T-01-06 | Tampering | Duplicate answer submission (double-tap / replay) creating extra points | mitigate | DB `UNIQUE (player_id, question_id)` on answers — second INSERT raises SQLSTATE 23505 regardless of API logic (SCOR-03). Verified by a deliberate duplicate INSERT test in Plan 03. (PITFALLS #5) |
| T-01-07 | Tampering | Duplicate player rows on reconnect/refresh | mitigate | DB `UNIQUE (game_id, device_token)` on players enables idempotent upsert (D-08). |
| T-01-08 | Elevation of Privilege | anon performing host-only writes (phase transition, reveal, reset) | mitigate | anon UPDATE/DELETE policies set to USING(false); reset_game() not granted to anon; all privileged writes go through the service-role server client which bypasses RLS by design (server-only per Plan 01). |
| T-01-09 | Tampering | RLS left at incomplete/ambiguous deny (silent empty reads) | mitigate | Explicit SELECT/INSERT/UPDATE/DELETE policies for anon on every table (PITFALLS #11), tested with anon key in Plan 03. |
</threat_model>
