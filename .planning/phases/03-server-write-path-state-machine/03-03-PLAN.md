<objective>
Deliver the host state-machine slice: `POST /api/host/transition` driving the full `lobby → question → locked → revealed → question → ended` machine with host-password auth (HOST-01/SC3), the D-07 compare-and-swap distinguishing rule (idempotent no-op vs illegal-409 vs CAS), atomic `current_question_id` assignment on start/advance, and a best-effort `GameEvent` broadcast per transition. After this plan the host can start, lock, advance, and end a game; double-clicking advances by exactly one step.

Purpose: `games.phase` is the canonical state machine and this route is its single legal mutator. The D-07 rule (record verbatim) makes the server the sole source of transition legality: same-target → 200 no-op (no scary error from a fat-finger double-tap, D-05), wrong expected-from → 409 + reason (a genuinely wrong control press is visibly rejected, D-06), otherwise a CAS `UPDATE ... WHERE id=:g AND phase=:expectedFrom` whose 0-row result is also treated as a 200 no-op (lost race). It depends on Plan 01's `validateHostAuth` and owns only `host/transition/route.ts`, so it runs in Wave 2 parallel with Plan 04 (reveal/reset).

Output: `src/app/api/host/transition/route.ts` (new).
</objective>

STEP 2 — D-07 rule: (a) if `game.phase === target` → idempotent no-op, return 200 `{ noop: true, state: game }` (D-05 — never throw on a benign double-tap); (b) else if `game.phase !== expectedFrom` → illegal, return 409 `{ error: "invalid_transition", current: game.phase, expected: expectedFrom }` (D-06 — machine-readable reason). STEP 3 — CAS UPDATE: build the update payload (`{ phase: target }`, plus the extra columns below) and run `adminClient.from("games").update(payload).eq("id", gameId).eq("phase", expectedFrom).select("phase, current_question_id")`. Use `.select()` WITHOUT `.single()` and detect the lost race with `if (!updated || updated.length === 0)` → return 200 `{ noop: true }` (D-07 third bullet; `.single()` would throw PGRST116 on 0 rows — Pitfall 1, Anti-Pattern). ATOMIC current_question_id (Pitfall 6): for `start` (lobby→question) the UPDATE payload must ALSO set `current_question_id` to the first question — fetch it first via `adminClient.from("questions").select("id").eq("game_id", gameId).order("display_order", { ascending: true }).limit(1).single()` (400/409 `no_questions` if none exist); for `next` (revealed→question) the payload sets `current_question_id = nextQuestionId` from the body; `lock` and `end` set only `phase`. STEP 4 — BEST-EFFORT BROADCAST (D-bcast): after a successful CAS, fire the matching `GameEvent` via `broadcast(\`game:${gameId}\`, "GAME_EVENT", payload)` inside a try/catch that logs and proceeds on failure (DB is source of truth; clients converge via subscribe-then-fetch).
